DESIGN ONLY — cloche-eiil

Group project tabs and the task stack by repository

Some Cloche projects declare more than one [[repositories]] entry in .cloche/config.toml — an app repo plus a nested checkout, for example. Today the console's project tab bar and task stack are keyed only by project: tasks from every repo in that project land in the same flat stack, distinguishable only by reading the task title. This ticket proposes three shapes for separating them, each shown against real projects and repos from this machine: manager (repos manager + repos/anarkana) and wrapped_cloche (repos wrapped_cloche + repos/cloche). Legacy single-repo projects — cloche, weave, job_huntr, candy — must render exactly as they do today.

The problem today: manager mixes tasks from its own repo and from repos/anarkana in one flat stack. The only clue is reading each task's title — nothing in the row structure says which repo it belongs to, and nothing in the tab bar hints that this project has more than one.

Option 1 — Nested tabs

A second tab row appears under the project row, but only for projects with more than one repository. It lists each configured repo plus an all repos pseudo-tab (the default, equivalent to today's merged view). Selecting a repo sub-tab scopes the stack to that repo only — the interleaving disappears rather than just being labelled.

Same shape applied to wrapped_cloche: sub-tabs read all repos · wrapped_cloche · cloche, URL /wrapped_cloche/cloche. Clicking a legacy project tab (cloche, weave, job_huntr, candy) shows no subtabs row at all — the body grid drops straight from the project tab row to the stack, identical to today's layout and height.

Legacy rendering

  • No [[repositories]] configured (or exactly one, the auto-seeded implicit default) → the subtabs row is omitted entirely, not collapsed-empty. Zero added height, zero added markup.

Keyboard

  • tab / shift+tab — cycle project tabs, unchanged.
  • r / shift+r — cycle repo sub-tabs (no-op on legacy projects); R jumps straight to "all repos".
  • j / k — move within the stack, unchanged; the stack itself is just shorter once scoped to one repo.

URL scheme

  • Legacy: /{project}/{task}, unchanged.
  • Multi-repo: /{project}/{repo}/{task}; omitting {repo} is a synonym for all (today's behavior). /manager ≡ /manager/all.
  • Deep links to a single repo's stack (/manager/anarkana) are bookmarkable — the strongest fit for the ticket's "interleaved and indistinguishable" complaint, since scoping removes the interleaving instead of just labelling it.

API additions

  • Projects list (tab bar): add repositories: [{name, path}] per project, sourced from config.Repositories / resolvedRepo (internal/adapters/grpc/repos.go) — needed to render the sub-tab row and its counts before any stack request.
  • Stack API: add a repository field to every stack entry (TaskStackNeedsYou/Running/Queued/Done, internal/adapters/web/handler_task_stack.go), matching RepositoryConfig.Name; legacy runs report an empty/omitted repo.
  • Stack endpoint needs a ?repo= filter (or repo-scoped route) plus per-repo aggregate counts (needs-you/running/queued/done) for the sub-tab badges — a new small aggregation, not just a filter, since today's counts are computed project-wide.

Option 2 — Grouped tabs

The project tab row stays one row. For a multi-repo project, its tab expands into a small group: a project label followed by repo segments in the same connected-strip style already used for the step strip in console-restructured-mock.html (.seg). The stack stays merged (no scoping, no "all repos" toggle needed) but each state group (Needs you / Running / Queued / Done) is subdivided by a thin repo header.

Clicking a segment (e.g. anarkana) filters the group headers shown, without leaving the project — URL becomes /manager/anarkana; clicking the project label or the other segment again clears the filter back to /manager. For wrapped_cloche the group reads wrapped_cloche [ wrapped_cloche | cloche ]. Legacy projects render as a plain .tab, exactly as before — no group wrapper, no segments, no repo headers in their stack.

Legacy rendering

  • Single/no repo → plain .tab, and the stack's state groups have no .repohead rows — identical DOM shape to today.

Keyboard

  • tab / shift+tab — cycle top-level project tabs/groups, unchanged.
  • → / ← — while a grouped tab has focus, step through its repo segments (filters group headers); no-op on plain tabs.
  • j / k — move within the stack, unchanged; still crosses repo headers when unfiltered.

URL scheme

  • Legacy: /{project}/{task}, unchanged.
  • Multi-repo, unfiltered: /{project}/{task} — same as legacy, since nothing is scoped by default.
  • Multi-repo, segment-filtered: /{project}/{repo}/{task}, same shape as Option 1's URL but semantically "filter the merged view" rather than "switch stack".

API additions

  • Same two additions as Option 1: repositories on the projects list, repository on each stack entry.
  • Per-repo aggregate counts for the segment badges (same new aggregation as Option 1).
  • Additionally: the stack response has to come back already ordered/grouped by repo within each state (or the client needs enough info — repo name is enough — to group client-side), which Option 1 and 3 don't require since they either scope server-side or don't group rows at all.

Option 3 — Repo as a stack facet

The project tab bar is untouched — no new row, no grouping, nothing to learn there. Each stack row gains a small repo chip next to its id. An optional filter strip of repo chips sits above the stack, shown only when the project has more than one repository, to collapse the list to one repo without leaving the page.

Same shape on wrapped_cloche: filter strip reads all · wrapped_cloche · cloche, rows carry a cloche or wrapped_cloche chip. Legacy projects show no filter strip and no chip column at all — the row grid stays [dot | id/title | elapsed], byte-identical to today's markup.

Legacy rendering

  • Single/no repo → the .repofilter strip and every row's .chip are omitted (not rendered empty). Cheapest of the three to keep legacy pixel-identical, since nothing about the tab row or the row grid changes shape.

Keyboard

  • tab, j, k — entirely unchanged.
  • r — cycle the repo filter chips (no-op on legacy projects); this is the only new binding.

URL scheme

  • /{project}/{task} everywhere, legacy and multi-repo alike — repo is an attribute of a task, not a scoping segment, and task ids are already unique within a project.
  • Filter state is a query param, /{project}?repo=anarkana, so it's shareable but optional — the canonical task URL never changes shape.

API additions

  • Only one: repository on each stack entry (same field as the other two options). No new aggregation endpoint — the filter strip can be built client-side from the repo names already present on stack rows, and per-repo counts are a client-side reduce over what's already fetched.
  • Projects list API can stay as-is; the tab bar doesn't need to know about repos at all.

Recommendation: Option 1 — Nested tabs

The ticket's complaint is that tasks from different repos are "interleaved and indistinguishable." A chip (Option 3) fixes indistinguishable cheaply but leaves the interleaving in place — you still scan past the other repo's rows to find what you want, just with a label to explain why they're there. Nested tabs (Option 1) fixes both: selecting a repo sub-tab removes the other repo's rows from the stack entirely, and "all repos" is still one click away for anyone who wants the merged view. It also produces the cleanest bookmarkable URL (/manager/anarkana) for the case this ticket is really about — sitting in one repo's context for a stretch of work.

Option 2 (grouped tabs) is a reasonable middle ground visually — it reuses the existing segmented-strip language from the step strip — but it's the most expensive to build (server-side grouping inside each state bucket, not just a filter) for a benefit (seeing both repos "at once, organized") that's mostly already available from Option 1's "all repos" tab.

Rollout note: all three options need the same first increment — a repository field on stack entries and repositories on the projects list — so Option 3's chip could ship first as the cheap, low-risk increment, with Option 1's scoped sub-tabs layered on top of the same data once it's proven out. They are not mutually exclusive: Option 1 could keep the chip in the "all repos" view for the same reason Option 3 has it.

Project and repo names (manager / repos/anarkana, wrapped_cloche / repos/cloche, cloche, weave, job_huntr, candy) are real, drawn from this machine's project registry and docs/CHANGELOG-DETAILED.md. Task ids, titles, elapsed times and counts are illustrative.
